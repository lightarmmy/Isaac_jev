# 以撒 Jev Demo：非视觉状态、动作与示范学习方案

资料核对日期：2026-11-23。用户倾向使用社区“忏悔龙” REPENTOGON。

后续已按用户提供的 TerraBlind 视频核对真实案例，见 [terrablind_review.md](terrablind_review.md)。模型规模建议以冻结 2B 为主线，使用同一批示范比较冻结 8B；状态桥接可参考 SocketBridge 的公开实现。

最新完整流程采用 DeepSeek API 高层决策、本地 RTX 4060 Laptop 8 GB 上的 2B 战斗模型、集群 L40S 训练；控制切换与数据闭环见 [isaac_hierarchical_pipeline.md](isaac_hierarchical_pipeline.md)。

## 可行性与版本

可以从真实游戏的房间战斗 Demo 开始。以撒的实时反应和几何控制要求较高，因此第一版需要同时验证状态质量、端到端延迟和闭环生存能力。

[REPENTOGON 当前 README](https://github.com/TeamREPENTOGON/REPENTOGON) 支持 Repentance+，是扩展游戏 Lua API 的社区 mod。实施时应固定游戏版本、REPENTOGON 版本、mod 和规则版本。

基础 API 已支持获取房间实体、实体位置/速度、玩家状态、房间障碍和输入，也支持通过 MC_INPUT_ACTION 覆盖游戏按键。仍需实机确认外部进程与 mod 的双向通信、状态采集时序及输入覆盖是否与当前版本和其他 mod 兼容。不能仅凭这些接口就声称 HTTP 或 socket 桥已经可用。

第一版建议：普通 Isaac、固定基础泪弹和移动属性、地下一层的小规模普通战斗房间。先包含地面接触敌人，再增加简单弹幕。先完成连续清房展示，再扩大到完整楼层和整局。

第一版暂不包含改变控制语义的蓄力武器、双角色、复杂主动道具和高密度 Boss 弹幕。这些需要扩展状态和动作定义。

## 1. 模型需要哪些信息

从 mod 获取结构化状态，使用游戏世界坐标，不依赖截图识别。

| 信息 | 初版字段 | 作用 |
| --- | --- | --- |
| 玩家 | 位置、速度、碰撞尺寸、血量、移动速度、伤害、射速、射击方向、控制是否可用、相关状态效果 | 判断移动、攻击能力与当前约束 |
| 房间 | 房间标识、形状、可走区域、墙/岩石/坑/尖刺/火焰、门位置与开闭、是否清房 | 避免穿墙、绕路和踩危险地形 |
| 敌人 | 稳定实体标识、类别、相对位置、速度、碰撞尺寸、血量、当前阶段、是否可伤害 | 选择攻击方向和规避路径 |
| 敌方投射物 | 位置、速度、碰撞尺寸、阵营、类型、必要的轨迹标志 | 短期躲弹 |
| 其他伤害源 | 激光几何形状与运动、爆炸/地面伤害范围、必要的当前阶段 | 避免把所有伤害源都误当成圆形子弹 |
| 历史与动作 | 近期状态、近期按键、上一条执行命令、房间内时间 | 表达惯性、持续射击和正在发生的动作 |
| 导航与资源，后续 | 可见拾取物、已探索地图、门、钥匙/炸弹/金币、道具功能与充能 | 清房后导航和资源选择 |

初版至少需要位置和速度。只有当前位置，无法区分向玩家接近和正在远离的弹幕。

敌人内部 State 数字不自动等于玩家能理解的动作。应为支持的敌人建立映射，例如接近、攻击预备、攻击中、落地、无敌；部分预兆可通过动画名称/帧和当前状态提取。取动画元数据不要求将画面送给视觉模型。

实体 Size/SizeMulti 可以辅助描述碰撞，但不能把所有敌人、激光和特殊效果都等同于精确圆形。初版限定支持的实体类型，并验证近似碰撞与实际受伤的一致性。

**保留原始状态，再生成模型摘要。** 保存完整原始状态便于后续重做特征，实时提示可以使用：

- 相对玩家的坐标和速度，统一单位与坐标方向。
- 临近且短期有威胁的敌人。
- 按接近程度/预测碰撞风险选取的投射物；不只按距离截断。
- 各移动方向的预计最近危险距离、障碍、攻击机会和风险估计可信度。
- 短历史和上次动作。

所有相关投射物仍可用于几何风险计算，模型提示再使用有界摘要。直线外推只能近似短期轨迹，遇到转向、追踪、反弹和阶段变化需降低可信度并重新计算。

规则以固定版本的前缀输入；第一版完整覆盖基础移动、射击、受伤、房间障碍以及所支持敌人/道具。规则规模随着支持内容增长，不预先将全游戏所有道具文档塞入每次实时输入。

## 2. 第一版动作定义

推荐固定的短时“移动 + 射击”联合动作，便于对齐用户操作和比较模型。

| 分量 | 选项 |
| --- | --- |
| 移动，9 类 | 停止、上、下、左、右、左上、右上、左下、右下 |
| 射击，5 类 | 不射击、上、下、左、右 |

这是普通键盘控制和基础泪弹的初版协议。若示范使用摇杆、模拟力度或特殊武器，应记录原始模拟输入，并明确量化和执行语义，不能直接假设上述协议完整覆盖。

**9 × 5 = 45 个组合。** 每个动作可以同时移动和射击，例如“右下移动 + 向左射击”。

优先用一个 45 类联合输出头，直接建模组合偏好。9 类与 5 类的两个头也可作对照，但独立输出会限制动作相关性的表达。

动作 ID 固定，不随每帧目标排序变化。协议保存语义映射和版本，不硬编码不同游戏版本的 ButtonAction 数值。

“保持当前动作”通过重新选择同一个联合动作实现，上一动作包含在状态中。每条命令有有限有效期，避免无限持续。

执行时覆盖正常游戏输入，让游戏本身处理移动、射击、碰撞与伤害。不通过直接设置 Position 实现瞬移。

动作返回示意：

```json
{
  "protocol_version": 1,
  "room_id": "room-17",
  "observation_frame": 1200,
  "action_id": 17,
  "move": "down_right",
  "shoot": "left",
  "hold_frames": 3,
  "valid_until_frame": 1203
}
```

示例 ID 仅为草案，正式协议需生成并验证完整映射。命令有效期以观测帧起算；响应到达时检查是否已过期，不在迟到后重新给它一段完整的持有时间。

## 3. 选项如何生成、数量如何确定

**初版 45 个固定组合不需要由语言模型生成。** 代码使用两组方向的笛卡尔积生成，训练头宽度固定为 45。

危险但仍可执行的移动一般保留为候选，并附风险；不要在规则层预先只留下“最安全”方向，否则模型实际只是在规则控制器的结果上评分。只有确定不可执行的操作才适合硬约束。

炸弹、主动道具、卡牌等后续另设输出字段或决策阶段。它们有按下/释放和冷却语义，不能因为每一帧预测“使用”而连续触发。

**坐标目标适合第二阶段导航。** 候选可来自可见门、拾取物、可走网格和局部站位点，经过可达性检查、去重及限额。模型选择目标，寻路控制器转成正常移动输入。

战斗坐标候选也可以来自玩家周围的 8 个方向、1–2 个距离圈，加当前位置，形成至多 17 个基础候选；考虑障碍和去重后数量变化。必须检查行走路径与预计执行期间的危险，不能只检查终点。此时需要支持变长候选的评分头。

直接从你的实际按键获得联合动作标签最清楚。高层坐标标签需要额外确定你当时想去哪里，或从未来轨迹推断目标并记录误差；这是一个不同的数据标注问题。

## 4. 实时执行频率

[MC_POST_UPDATE 文档](https://wofsauge.github.io/IsaacDocs/rep/enums/ModCallbacks.html#mc_post_update) 指明游戏逻辑更新为 30 Hz；渲染回调是 60 Hz。

初始实验可使用 3 个逻辑帧约 100 ms 的短动作块，在约 10 Hz 做决策。根据人类动作稳定性和实测效果，再比较 1、2、3 帧持有策略。100 ms 是实验起点，不是保证足以躲避所有攻击的结论。

需要测量完整链路：状态采集 → 通信 → tokenization → Qwen 前向 → 决策头 → 返回 → 游戏实际输入生效。不能只测分类头耗时。

如果要每逻辑帧做一次独立决策，持续的端到端周期需要支持约 33 ms 的预算，并关注 P95、状态年龄与队列积压。远程 GPU 的网络往返同样算入预算。

推理驻留并预热；只处理最新状态，不将旧帧请求不断排队。换房、暂停、失去控制时清理旧命令。输入回调频繁触发，只读取当前已缓存命令，不在 MC_INPUT_ACTION 内阻塞等待模型。

如果加入逐逻辑帧运行的几何避险层，必须记录它覆盖模型动作的原因和比例，分别评价纯模型与组合系统。该层可以帮助实时性，但会改变系统能力的归属。

## 5. 用你的操作做示范学习

不必从零强化学习开始。第一条训练路线是行为克隆：

```text
完整模式规则 + 状态/短历史
              ↓
        冻结 Qwen 文本主干
              ↓
       可训练 MLP 决策头
              ↓
        45 类联合动作概率
```

MLP 头可以同时接收标准化的数值特征和上次动作。若加入 GRU，需要按连续序列训练，并在换房/重置时清除记忆。第一版无需为模仿学习加入 PPO 价值头。

冻结 Qwen 省去主干反向传播，但推理仍需计算主干。固定主干的表示未必充分表达几何与运动关系，只训练线性头不保证成功；先比较 MLP 头和一个小型数值状态策略作为基线。如果冻结方案达到瓶颈，再考虑 LoRA。

采集与训练：

1. **30 Hz 记录原始状态和原始输入。** 移动/射击使用持续按键值，炸弹等另记录触发边沿。保存 game_frame、room_id、run_id、控制模式、规则和协议版本、必要的时间戳。
2. **验证时序。** 每个训练样本中的 s_t 应在对应动作生效之前；不能拿动作执行后的状态去预测此前按键。明确每个回调阶段对应的物理更新顺序，并用简单移动探针检验。
3. **处理动作块。** 先保存逐帧输入，再按目标持有周期生成样本；统计块内按键变化，不用多数投票消掉关键躲避动作。短时变更多的片段可以使用更短动作块或序列输出。
4. **训练 MLP 头。** 对你的动作标签做交叉熵；检查类分布，避免“不动/持续某方向射击”占满数据。适当增加危险、转向、卡墙、攻击对齐和恢复片段的采样权重。
5. **按整局或房间划分数据。** 相邻帧不能随机分到训练与测试中；保留新房间配置和新初始化作为泛化测试。
6. **先做影子预测，再做闭环。** 你正常操作时记录模型预测；然后让模型控制，在它进入失误状态时由你接管并记录修正操作。迭代补充模型自己遇到的状态，这是 DAgger 风格的数据收集。

一小时约有 108,000 个 30 Hz 逻辑帧；按 10 Hz 对应约 36,000 个决策点。这只是数量，不代表独立有效样本或足够覆盖所有情况。场景覆盖比连续录同一种房间更重要。

受伤和失败片段要标记，不把失败对局整段删除；模型也需要学习从不理想位置恢复。未来结果可以作为标签或质量统计，不能作为当时可观察输入。

冻结主干训练时可以预计算 h_t，之后多轮训练只读取特征和标签。若后续换规则、状态格式、主干或引入 LoRA，需要重新生成相应特征。

策略 softmax 表示动作选择分布，不等于无伤概率或通关概率。

## 6. 首版验收与阶段

1. 输入/状态探针：实机核实坐标、速度单位、碰撞尺寸、30 Hz 时序、持续按键与输入覆盖。
2. 示范采集：你操作，完成几种简单房间，导出原始数据和状态摘要。
3. 行为克隆：冻结主干训练 45 类 MLP 头，完成影子预测和延迟测试。
4. 闭环清房：记录成功率、受伤次数、清房时间、卡墙时长、动作切换率、状态年龄、P50/P95 延迟和接管次数。
5. 接管补数据后复测，再扩展到楼层导航、资源与新武器。

展示可叠加候选动作概率、当前选定动作、危险摘要和延迟；画面供人观看，模型输入仍是结构化状态。

当前完成的是文档核对和实施设计，尚未安装 REPENTOGON、运行通信桥、采集示范、训练模型或实测 L40S。
